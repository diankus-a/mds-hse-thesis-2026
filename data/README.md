# Детекция дублей в аналитических таксономиях

**ВКР:** Разработка инструмента для автоматической идентификации дублирующихся событий  
и проверки стандартов именования в аналитических таксономиях

## Датасет

### Источник

Датасет `taxonomy_duplicates_balanced.csv` сформирован на основе реальной таксономии (область фин-тех)   
(4027 уникальных событий из производственного трекинг-плана) методом контролируемой аугментации.

### Описание

| Параметр | Значение |
|---|---|
| Всего пар | **50 000** |
| Дублей (label=1) | **25 000 (50%)** |
| Не дублей (label=0) | **25 000 (50%)** |

| NaN | 0 |
| Дублирующихся пар | 0 |


## Ключевые выводы EDA

1. **Датасет чистый**: нет NaN, дублирующихся пар, идеально сбалансирован 50/50.

2. **Overlap-зона**: 24.3% пар имеют `char_sim ∈ (0.65, 0.90)` — это самая трудная область для классификации. Здесь смешиваются `semantic`, `permutation` и `not_duplicate`.

3. **Тип `case` — высокая дисперсия**: форматы `flatcase` и `UPPERCASE` дают `char_sim ≈ 0`, несмотря на то что это дубли. После нормализации `norm_sim → 1.0`.

4. **Семантика недоступна строковым методам**: `semantic`-пары имеют char_sim = 0.734, но часть из них (например, `login_success` / `user_authenticated`, sim ≈ 0.19) строковыми методами не детектируется.

5. **Цель следующего этапа**: обучить SBERT-модель, которая преодолеет потолок строковых методов на `semantic` и `case(flatcase/UPPERCASE)` типах.

## Промпт генерации датасета
Задача: 
Сгенерировать размеченный датасет пар событий для обучения модели 
бинарной классификации дублей в аналитической таксономии.
Метод формирования: контролируемая аугментация на основе реальных данных.

Источник данных:
Файл с реальными аналитическими событиями банка в формате:
[ObjectPath] [Action] — последний токен является глаголом-действием,
всё предшествующее описывает объект или экран.

Требования к датасету:
- Размер: ровно 50000 строк
- Формат: CSV с колонками event_1 (str), event_2 (str), 
  label (int: 1=дубль, 0=не дубль), dup_type (str)
- Без NaN, без дублирующихся пар
- Стратифицированное распределение по dup_type

Распределение типов:
not_duplicate  — 30% (15000 пар)
typo           — 15% (7500 пар)
synonym        — 15% (7500 пар)
permutation    — 15% (7500 пар)
semantic       — 15% (7500 пар)
case           —  9% (4500 пар)
exact          —  1% (500 пар)

Правила генерации каждого типа:
exact:
Точное совпадение: event_1 == event_2.
Seed: случайная выборка из реальных событий.

typo:
Ровно одна опечатка в snake_case строке, не затрагивающая символ '_'.
Допустимые операции (выбираются случайно равновероятно):
- delete: удаление одного символа
- double: дублирование одного символа
- swap: транспозиция двух соседних символов
- replace: замена символа на соседний по клавиатуре (QWERTY-маппинг)
Ограничение: результирующая строка длиной > 3 символов.

case:
Конвертация snake_case в один из 8 форматов именования
(равномерно, ~562 пары на формат):
lowerCamelCase | PascalCase | SCREAMING_SNAKE_CASE |
kebab-case | Train-Case | flatcase | UPPERCASE | space case
Алгоритм: разбить по '_' → применить форматирование → проверить
что результат отличается от исходника.

synonym:
Замена любого токена на синоним
Ограничение: char_sim результирующей пары должен быть > 0.55.

permutation (label=1)
Перестановка двух токенов
Условия: длина события ≥ 4 токенов, расстояние между
переставляемыми позициями ≥ 1, результат отличается от исходника.

semantic
Три источника в порядке приоритета:
1. Реальные данные: пары из одного объектного пути с разными actions. Исчерпать полностью.
2. Word-synonym подход: замена 1–2 токена на синоним
   Ограничение: char_sim < 0.82 (отличие от synonym-типа).
3. Full-synonym: пример login_success/user_authenticated и др., ≥ 40 пар.

not_duplicate

После генерации каждого типа — trim до целевого количества через стратифицированную выборку
